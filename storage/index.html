    FGHPC Storage¶

    FGHPC combines large shared filesystems on master with high-capacity local disks and NVMe devices on the execution nodes, and a BeeGFS parallel scratch filesystem spread across the compute nodes' NVMe. The same pathname can therefore mean very different things operationally: durable shared data, an AutoFS view, shared scratch, or disposable node-local working space.

    Current production state

    Durable shared storage uses NFSv4 and AutoFS over dedicated ConnectX-5 links. BeeGFS is deployed (September 2026) as the cluster's parallel scratch tier: two filesystems — /nvme (21 TB) and /nvme_vf (2.7 TB) — backed by the NVMe of node1–node3, with management and metadata on master. Clients are live on master and gpunode1; client mounts on node1–node3 are still being finalized. BeeGFS is scratch: fast and shared, but disposable — never the only copy of your data.

    Storage at a glance¶

    Tier Location Capacity in inventory Visible from Primary purpose
    BeeGFS parallel scratch /nvme + /nvme_vf (NVMe of node1–node3) 23.7 TB all nodes as BeeGFS clients high-throughput intermediates: alignments, sorting, pipeline temp files
    User homes master:/home, ZFS pool homefs 3.4 TiB usable master and workers through per-user AutoFS user configuration, scripts, small files
    Active shared data master:/nfs_master 174 TiB all workers through NFS active projects and workflow outputs
    Large shared data master:/Fungel 212 TiB all workers through NFS large datasets, references, archive-oriented storage
    Shared applications master:/apps part of 1.8 TiB root filesystem workers at /nfsroot/apps through AutoFS centrally managed software and modules
    CPU-node local RAID /DATA about 73 TiB per CPU node that node only large temporary or node-local work
    CPU-node local NVMe /NVME_DATA1, /NVME_DATA2 about 3.5 TiB each that node only high-I/O intermediates
    CPU-node local NVMe /NVME_DATA3 about 916 GiB that node only additional local working space
    GPU-node local data gpunode1:/DATA about 7.3 TiB gpunode1 only GPU-local staging and temporary data

    Capacities and utilization are inventory snapshots, not quotas or guarantees. Always check live values before starting a large workflow.

    How data reaches a job¶

                       master
     ┌───────────────────────────────────┐
     │ ZFS /home                         │
     │ ext4 /nfs_master                  │
     │ ext4 /Fungel                      │
     │ XFS / containing /apps            │
     └───────────────┬───────────────────┘
                     │ NFSv4 / AutoFS
          dedicated 192.168.x.0/24 links
                     │
       ┌─────────────┼─────────────┬─────────────┐
       │             │             │             │
     node1         node2         node3       gpunode1
   shared mounts + local RAID/NVMe         shared mounts + local /DATA

    The master copy is authoritative for shared paths. Local worker storage is not automatically synchronized to any other node.

    BeeGFS adds a second, parallel scratch tier on top of the NFS tree. Its management and metadata services run on master; the actual bytes live on the NVMe of node1–node3, and every node mounts it as a client:

            master (management + metadata)
                    │
   ┌────────────────┼────────────────┐
   │                │                │
 node1            node2            node3
 NVMe storage     NVMe storage     NVMe storage
   └────────────────┴────────────────┘
                    │
        striped namespace, mounted by all nodes
        /nvme  (21 TB)   +   /nvme_vf  (2.7 TB)

    Use /nvme and /nvme_vf for the fast, throwaway middle of a workflow — intermediates, sorting, alignment — and keep the only durable copy on NFS.

    Choose the right page¶

    • Shared storage: how /home, /nfs_master, /Fungel, and /apps are built and exported.
    • Local worker storage: exact /DATA and NVMe layout by node.
    • BeeGFS scratch (/nvme, /nvme_vf): parallel, shared, disposable — see data placement for what belongs there.
    • Mount architecture: NFS sources, AutoFS behavior, dependencies, and validation.
    • Capacity and health (monitored by the admin; ask if your job feels slow), ZFS, NVMe, and failure boundaries.
    • Storage recovery: safe diagnosis after reboot or mount failure.
    • Storage best practices: where researchers should place data and why.

    Fast live check¶

    fghpc storage
df -hT
df -ih
findmnt -T /home
findmnt -T /nfs_master
findmnt -T /Fungel
findmnt -T /apps
findmnt -T /nvme
beegfs-df
fghpc beegfs

    On workers, trigger AutoFS using a real child path such as /home/USERNAME or /nfsroot/apps; checking only /home does not prove a user's NFS mount works.
